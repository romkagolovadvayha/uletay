### 1. P1 — обновить уязвимые серверные зависимости

В сохранённом актуальном `npm audit --omit=dev` для CMS отмечены три пакета: Next.js — critical, Sharp — high, mysql2 — moderate. Для Next.js присутствуют два отдельных критических advisory.

- Установленный Next.js 16.3.2 попадает в диапазон ошибки выполнения кода на Windows. Описанный в репозитории production-деплой использует Ubuntu, поэтому именно Windows-сценарий нельзя автоматически переносить на него. Исправление опубликовано в 16.3.3. [Advisory Next.js для Windows](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36).
- Второе advisory связано с обработкой AVIF через Image Optimization API и Sharp/libheif. Оно не ограничено Windows. Исправленная версия Next.js — 16.3.3. [Advisory Next.js для AVIF](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4).
- Sharp до 0.35.4 использует уязвимую зависимость обработки HEIF/AVIF; условия эксплуатации зависят от входного файла и среды. В CMS есть собственная обработка загруженных файлов через Sharp. Проверка MIME/расширения сама по себе не запрещает декодирование содержимого другого формата. [Advisory Sharp](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c).

**Действие:** обновить Next.js минимум до 16.3.3 и Sharp минимум до 0.35.4, проверить фактически установленные копии и lockfile, затем сборку CMS и загрузку изображений. Если обновление Sharp откладывается, официальный advisory описывает временный запрет HEIF-декодера. Эксплуатация уязвимостей на сервере в этом аудите не проверялась и не утверждается.

Для mysql2 проблема относится к сжатому протоколу; в [db.ts](C:/xampp/htdocs/uletay/cms/src/lib/db.ts:9) сжатие явно не включено. Это снижает приоритет относительно двух предыдущих пакетов. Обновлять следует до версии вне диапазона сохранённого advisory и проверять подключение/миграции.

Это **не 26 независимых уязвимостей пользовательского приложения**: часть результатов относится к цепочкам Expo/Metro и инструментам сборки. Не применять `npm audit fix --force` вслепую: предлагаемые автоматические варианты включают несовместимые изменения основных пакетов. Обновлять совместимыми группами с проверкой Expo и отдельных advisory.

### 2. P1 — объединить offline и push в один service worker

[installWebOffline.ts](C:/xampp/htdocs/uletay/src/utils/installWebOffline.ts:81) регистрирует `/sw.js` с областью `/`. [remotePushNotifications.ts](C:/xampp/htdocs/uletay/src/utils/remotePushNotifications.ts:74) регистрирует `/push-sw.js` с той же областью. Один worker содержит обработку fetch/кэша, второй — push и клика по уведомлению. При одинаковой области новая регистрация меняет существующую. Это соответствует поведению [ServiceWorkerContainer.register](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/register).

**Воспроизведено в Chrome:** после `/sw.js` запрос данных без сети успешен; после регистрации `/push-sw.js` остаётся одна регистрация с активным push-worker, и тот же офлайн-запрос перестаёт работать. Фактическая доставка push не использовалась в проверке.

**Действие:** один worker с fetch, push и notificationclick; продумать переход уже установленных клиентов. Проверка исправления: включить уведомления, перезагрузить приложение, отключить сеть, открыть кэшированные разделы; уведомление должно открывать нужный маршрут без потери офлайн-режима.

Дополнительно убрать зависимость инициализации только от будущего события `window.load`: функция вызывается из React effect и может выполниться после этого события. При `document.readyState === 'complete'` инициализацию нужно запускать сразу.

### 5. P1 — защищать сохранение CMS от потери параллельных правок

[saveAppData()](C:/xampp/htdocs/uletay/cms/src/lib/app-data.ts:117) безусловно заменяет весь JSON одной записью `UPDATE`. Проверки версии, на основе которой подготовлены изменения, нет.

**Воспроизведено:** два независимых снимка прочитаны из одной версии. В первом изменено название, во втором — место проведения. После двух сохранений правка названия исчезает. Это моделирует независимые процессы редактора/синхронизации; тест не утверждает, что любое одновременное действие в одном процессе обязательно теряет данные.

**Действие:** добавить монотонную `revision`, сохранять с условием `WHERE revision = expectedRevision`, проверять `affectedRows`, показывать конфликт вместо молчаливой перезаписи. По возможности записывать изменения конкретной сущности. Такая версия также надёжнее текущего сравнения секундного `updated_at` для межпроцессного кэша.

**Критерий:** два редактора и фоновая синхронизация либо сохраняют совместимые изменения, либо получают явный конфликт; тихой потери данных нет.

### 15. P2 — отменять незавершённый запуск наблюдения за геолокацией

## Производительность и структура

Измерения сделаны по свежему локальному web-экспорту и seed-данным; это размеры файлов, не полевые Core Web Vitals и не измерение трафика production.

| Объект | Без сжатия | gzip |
| --- | ---: | ---: |
| Основной JS `index-…js` | 2 171 454 байта | 496 824 байта |
| Отдельный JS карты | 152 336 байт | 39 187 байт |
| Клиентский JSON из локального seed | 848 376 байт | 159 390 байт |

Зоны карты занимают примерно 377 КБ, артисты — 362 КБ несжатого JSON. Они вместе составляют большую часть общего ответа, даже когда пользователь открывает только настройки или радио.

Предлагаемый порядок оптимизации:

1. Разделить часто обновляемое расписание, карту и архив артистов на независимо кэшируемые данные. Главной странице достаточно краткого представления артистов; историю/треки получать при открытии карточки.
2. Выделить минимальный офлайн-набор и показывать состояние его загрузки. Проверять наличие нужных модулей, данных и ресурсов перед надписью «Доступно без сети».
3. Профилировать основной JS на Android среднего класса. Карта уже вынесена в отдельный chunk; оценивать пользу дальнейшего разделения по измерениям, учитывая требование офлайн-доступа.
4. Уменьшить набор глифов иконок и веб-шрифтов. После текущей очистки остаются четыре TTF приблизительно по 0,33–0,39 МБ. При изменении формата обязательно сохранять кириллицу и реальные начертания.
5. Проверить паузу фонового видео при скрытой вкладке, экономии трафика и сниженной анимации. Сначала показывать статический кадр, чтобы видео не конкурировало с данными и навигацией.

Крупные модули (`MapDrawEditor`, действия CMS, экран карты, отправка push, радио) стоит постепенно разделять по ответственности. Общие типы и схемы данных приложения/CMS — хороший первый кандидат на общий модуль. Полное дробление JSON по SQL-таблицам не является обязательным первым шагом: контроль версии и правильные границы записи решат главную проблему быстрее.

Дополнительная небольшая ошибка конфигурации: [schema.sql](C:/xampp/htdocs/uletay/cms/scripts/schema.sql:1) жёстко использует базу `uletay`, хотя окружение и деплой позволяют задавать `DB_NAME`. Нужно согласовать установку схемы с выбранной базой и проверить установку на имя, отличное от `uletay`.

## Интерфейс и продукт

Сохранять чёрно-жёлтый стиль и узнаваемую главную. Предлагаемые изменения решают конкретные задачи посетителя:

- **Главная:** рядом с артистами явно писать «Архив фестиваля 2026» и «Лайнап 2027 ещё не объявлен». Сейчас заголовок 2026 корректен, но подпись «Анонсированные артисты фестиваля» под блоком на главной 2027 допускает неверное прочтение. На отдельной странице лайнапа нужное пояснение уже есть.
- **Карточки артистов на телефоне:** дать имени до двух строк; статистику прослушиваний сократить до второстепенной подписи. Сейчас длинные имена и числа обрезаются одновременно. Для выбора концерта полезнее сцена, время и действие добавления в избранное.
- **Главная во время фестиваля:** ближайшие избранные выступления, текущая сцена/время и быстрый маршрут. Существующие сезонные состояния сохранить, но проверить их с конкретными данными до начала, во время и после события.
- **Десктоп:** ограничить ширину длинных списков или использовать две колонки, чтобы карточки не растягивались на весь оставшийся экран. Ширину бокового меню согласовать с плотностью содержимого.
- **Настройки:** демо-время перенести ниже повседневных действий или в отдельный пункт; состояние уведомлений и готовность офлайн-данных показывать выше. Добавить время последней успешной синхронизации и понятный статус ошибки.
- **Карта:** показать источник/примерность ETA, сохранить понятный fallback при отсутствии GPS и маршрута; пользовательские точки сделать легко управляемыми. Отдельно проверить крупный системный шрифт и управление экранным диктором на настоящем телефоне.

## Порядок работ и проверки приёмки

**Первый пакет — стабильность и защита релиза.** Обновить Next.js/Sharp, объединить worker, исправить восстановление ленивых экранов и веб-сброс кэша. Закрыть произвольные push-endpoint, включить ограничение попыток входа и строгую проверку production-секрета.

**Второй пакет — надёжность контента.** Независимые снимки кэша, версия данных при сохранении, runtime-схема и журнал изменений с восстановлением. Одновременно исправить суммирование маршрута и валидацию/тайм-аут API.

**Третий пакет — эксплуатация.** Атомарные релизы и откат; наблюдение за ошибками API/клиента с версией сборки, временем ответа и контекстом маршрута. Регулярно проверять восстановление резервной копии БД и uploads. Не отправлять координаты/токены в диагностические журналы без необходимости.

**Четвёртый пакет — скорость и удобство.** Разделение данных, устранение обновлений без изменений, измерения на устройстве, согласование сезонов/архива и доработка карточек.

В CI добавить проверки, которые непосредственно предотвращают обнаруженные регрессии:

- Совместная регистрация worker, офлайн-переход на новый экран и восстановление после ошибки chunk.
- Ошибка записи БД не меняет кэш; два сохранения одной revision не теряют данные молча.
- Повреждённый JSON, неправильный GeoJSON и ссылки на отсутствующие сущности не сохраняются.
- Loopback/private push-endpoint и отсутствующие координаты маршрута отклоняются до обращения к внешним сервисам.
- Несколько участков маршрута дают полную геометрию, расстояние и время.
- Уже существующие `test:sw`, `test:api-url` и проверки карты запускать вместе с текущими проверками push и SEO.
- Проверять старую открытую вкладку после публикации новой версии и неудачную активацию релиза.

До публикации мобильной версии нужен отдельный проход на Android: холодный запуск, отказ в GPS/уведомлениях, возвращение из фона, радио, напоминания, быстрый уход с карты, режим без сети. Для iOS требуется собственная проверка сборки и разрешений.
