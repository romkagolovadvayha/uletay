# Live Activity: обновление и завершение через APNs

Изменения подготовлены локально. Сервер и приложения пока не опубликованы.

## Как это работает

Приложение создаёт карточку локально с `pushType: .token`. Кнопки, таймер и включение уведомлений не ждут сеть. Нативная часть наблюдает `pushTokenUpdates` и состояние карточки, сохраняет анонимную идентичность установки в Keychain и отправляет регистрацию через URLSession. Работа не зависит от JavaScript. После перезапуска восстанавливаются наблюдатели существующих активностей; неудачная регистрация повторяется при следующей синхронизации/возвращении в приложение. Обычные токены Expo Push здесь не используются.

Сервер читает актуальное расписание. Фоновый процесс раз в минуту отправляет изменение сцены, артиста, времени или фазы события и команду `end` с `dismissal-date` после окончания, удаления события или отключения. В карточке обновляемые данные находятся в ContentState, а не в неизменяемых attributes. Даты Foundation Codable используют стандартную эпоху 2001 года; время в оболочке APNs использует Unix epoch. Протокол проверяется настоящим Swift JSONDecoder.

Один процесс использует до двух HTTP/2-соединений (production/sandbox) и до 16 параллельных потоков. Очередь хранится в MySQL, выдаёт аренду задания, исключает повторные отправки и ограничивает один проход примерно 45 секундами. Ошибки повторяются с задержкой; недействительные токены исключаются. Для массовой доставки не создаются сотни новых TLS-соединений. Обычные web-напоминания запускаются отдельным cron-заданием и не задерживают эту очередь.

## Настройка перед будущим развёртыванием

1. Получить доступный команде Apple APNs signing key, которому разрешён topic `ru.uletay.app.push-type.liveactivity`. Ключ App Store Connect для загрузки приложения не подходит. У приложения уже настроена capability Push Notifications.
2. Установить `.p8` вне публичных каталогов и репозитория, например `/etc/uletay/apns/AuthKey.p8`. Дать доступ только пользователю фонового процесса.
3. Заполнить `FESTIVAL_ACTIVITY_APNS_TEAM_ID`, `FESTIVAL_ACTIVITY_APNS_KEY_ID`, `FESTIVAL_ACTIVITY_APNS_KEY_PATH` в серверном окружении. На телефоны эти значения и ключ не передаются. `FESTIVAL_ACTIVITY_APNS_ENABLED` пока оставить `false`.
4. Применить штатную миграцию CMS: `npm --prefix cms run db:migrate`. Она создаст две таблицы из `cms/scripts/live-activities-schema.sql`, не меняя существующие push-подписки или расписание.
5. При разрешённом развёртывании выполнить существующий `deploy/setup-push-reminders-cron.sh`: он установит отдельный запуск `send-festival-activities.ts` раз в минуту и ротацию `live-activities.log`.
6. Включить серверный флаг `FESTIVAL_ACTIVITY_APNS_ENABLED=true` и затем распространять новую нативную сборку приложения.

При развёртывании `deploy/remote-deploy.sh` сохраняет четыре host-local настройки APNs из предыдущего `.env`. Ключ остаётся вне каталога релизов. Результат конкретного развёртывания фиксируется в отчёте выпуска. Автоматические тесты сервера используют локальную БД и подменённый APNs; реальные пользователи тестовых сообщений не получают.

## Безопасность и совместимость

- Регистрация защищена отдельным случайным секретом установки из Keychain; сервер хранит только его SHA-256. Монотонная ревизия не позволяет запоздавшему запросу отменить отключение. После переустановки сохранённая Keychain-идентичность корректно восстанавливает счётчик ревизий.
- Клиент передаёт идентификатор события, но не может задавать текст серверного push: данные берутся из расписания CMS.
- Токены и секреты не попадают в журналы. Завершённые активности удаляются через 2 дня, заброшенные установки — через 30 дней.
- iOS URLSession отправляет регистрационные данные только собственному HTTPS API; loopback HTTP разрешён только DEBUG-сборкам.
- Старые мобильные сборки продолжают локальную работу, Android не регистрирует APNs. Новые необязательные поля ContentState поддерживают старые карточки с одним `endAt`.
- Устаревший кэш после возвращения в приложение не перезаписывает более свежую карточку APNs. Явное отключение или удаление из избранного обрабатывается локально сразу. Скрытая пользователем карточка не создаётся заново при обычном обновлении расписания.

## Проверки

- `npm run test:notification-settings`
- `npm run test:push-registration`
- `npm run test:festival-activity`
- `npm run test:festival-activity:bridge`
- `npm --prefix cms run test:live-activities`: настоящий HTTP/2 mock APNs, подпись ES256, заголовки, payload, sandbox/production, ошибки 410 и 429.
- `npm --prefix cms run test:live-activities:db`: изолированный MySQL 8 на loopback:3347; тест создаёт и удаляет только БД `uletay_activity_test_<uuid>`. Проверяет SQL, ревизии, права установки, параллельных работников, повторы, отключение, удаление события, завершение без клиента и реальные обработчики маршрута Next.
- Профиль EAS `ios-live-activity-qa` собирает simulator-приложение и исполняет `scripts/festival-activity-protocol-checks.swift`. Он не увеличивает номер сборки, не загружает приложение в App Store Connect и не отправляет его на модерацию.

## Границы

Эта реализация обновляет и завершает уже созданную или локально запланированную карточку. Запуск первой карточки сохраняет условия существующего приложения: foreground, либо локальное планирование следующего события на iOS 26. Отдельный push-to-start для запуска новых карточек на iOS 17.2–25 здесь не включён.

При работающем cron изменение обнаруживается обычно в пределах минуты. Доставку и задержки APNs определяет Apple; без сети доставка не гарантируется. Таймер и staleDate остаются локальным резервом. Конечная команда хранится APNs до 4 часов и заменяет устаревшие команды той же активности. Полная проверка на физическом iPhone с настоящим APNs остаётся этапом перед выпуском; публикация не заменяет её.
