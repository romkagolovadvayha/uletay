# УЛЕТАЙ: аудит проекта и план развития

Дата: 5 сентября 2026 года. Объект: текущая рабочая копия `C:\xampp\htdocs\uletay`.

## 1. Вывод

Проект уже представляет собой полноценный цифровой гид фестиваля: Expo-приложение для web/iOS/Android, Next.js CMS и API, MySQL, расписание, карта территории, избранное, радио, уведомления, справочная информация и инструменты публикации.

Рекомендуемое направление: сохранить существующую архитектурную основу и фестивальную стилистику, сначала устранить риски достоверности данных и работы без сети, затем упростить основные сценарии и обновить интерфейс. Наибольшую пользу дадут удобное расписание, понятное «Моё», надёжная карта и безопасное редактирование программы.

Это аудит и предложение изменений. Продуктовый код, зависимости, настройки уведомлений, база данных и production не изменялись.

## 2. Объём и ограничения проверки

Изучены структура репозитория, конфигурация Expo SDK 57, навигация, контексты данных/избранного/деморежима, расписание и время фестиваля, карта, каталог артистов, фудкорт, помощь, радио, UI-токены, серверная авторизация, хранение контента, загрузка медиа, push, SEO-генерация и workflow деплоя. В каталоге screens находится 19 экранов.

В браузере открыта актуальная локальная dev-версия. Визуально проверены главная, расписание, карта, каталог артистов, радио, меню «Ещё», помощь. Проверены ширина 390×844 и исходное окно 1280×720; выполнен поиск без результатов и короткая проверка клавиатурного фокуса меню.

В открытом браузере уже был сохранён деморежим. Баннер «Данные вымышлены» отображался. Тестовые выступления и время не считаются фактической программой фестиваля. Деморежим по умолчанию в коде выключен. Я не переключал пользовательские настройки.

CMS оценена по исходникам и её собственному TypeScript-компилятору. Авторизованная работа редактора в браузере, реальные iOS/Android-сборки, доставки push на устройства, восстановление production-БД и нагрузочные испытания не проверялись. Визуальный осмотр не является полным подтверждением WCAG. Производительность production по Lighthouse/Core Web Vitals не измерялась; задержки компиляции dev-сервера не принимались за скорость продукта.

## 3. Что уже сделано хорошо

- Разделены клиент, CMS/API и эксплуатационные скрипты. Next.js и Expo подходят текущей задаче; обязательной миграции на другой стек не видно.
- Есть общие цвета, шрифты, отступы, радиусы, стили и переиспользуемые элементы интерфейса.
- Фестивальное время выделено отдельно: Europe/Samara и начало фестивального дня в 04:00. Это полезная основа для ночной программы.
- Есть локальный кэш, повторные запросы и защита от части дублирующих запросов.
- Главная умеет показывать ошибку обновления и время ранее полученных данных.
- Экран артистов использует FlatList, поиск, фильтр года и сортировку; есть понятный ответ на пустой результат поиска.
- Поддерживаются reduced motion, отложенная загрузка hero-видео, некоторые ограничения для слабой сети, отложенная загрузка экранов.
- Используется expo-image; для загрузок CMS формируются WebP и уменьшенные варианты изображений.
- Карта имеет обработку ошибок, категории, пользовательские места, маршруты и добровольный запрос геолокации.
- Есть справка и экран помощи с понятными крупными действиями.
- CMS использует bcrypt, случайные bearer-токены, HttpOnly cookie и параметризованные SQL-запросы в просмотренных операциях.
- Перед массовым push есть подтверждение; имеются история рассылок и счётчики принятых/ошибочных сообщений.
- Деплой проверяет конфигурацию, выполняет lint/typecheck, сборки и часть тестов. Есть закреплённый SSH host key, HTTPS и security headers.
- SEO уже включает отдельную инфраструктуру маршрутов, метаданных, sitemap и структурированных данных. Предложение «добавить SEO с нуля» здесь было бы неверным.

## 7. Предлагаемое направление дизайна

Характер: музыкальный фестиваль, живая фотография, контрастная типографика, жёлтый фирменный акцент. Для действий на территории важнее быстрое чтение с телефона на улице, чем декоративная выразительность.

### Цвета и поверхности

Сохранить жёлтый `colors.primary = #FFC107`. Чёрный фон допустим для фестивального образа и OLED; его замена сама по себе не исправит UX. Для прототипа сравнить текущий чёрный и графитовый `#101113` при дневном освещении.

Развести `surface`, `surfaceElevated`, `surfaceMuted` по роли. Сейчас несколько поверхностей имеют одно значение `#1C1C1E`. Активный выбор — жёлтый, срочное сообщение/LIVE — красный, цвет сцены — только принадлежность сцене. У каждого статуса остаётся текстовая подпись.

Не менять существующий набор Ionicons без практической причины. Единые размер, толщина и состояния важнее замены библиотеки иконок.

### Типографика

- Оставить Montserrat для узнаваемости и крупных фестивальных заголовков.
- `typography.body`: прототипировать 16/24 вместо текущих 14 без общей lineHeight.
- `typography.caption`: 13/18; `scheduleTime`: 14/18, полный интервал; имя в списке: 16/20.
- Капс оставить для коротких заголовков и маленьких статусов; инструкции, длинные названия и подписи писать обычным регистром.
- Не уменьшать шрифт, чтобы вместить семь вкладок: сократить число вкладок.
- Прошедшее выступление остаётся читаемым; гасить можно акцент и фон, но не весь компонент.

### Размеры и компоненты

- Основное действие 48–52 px высотой; самостоятельная зона нажатия иконки 44–48 px как продуктовая цель.
- Шкала отступов 4/8/12/16/24/32. Между разделами больше воздуха, чем внутри карточки.
- Текст и кнопки не должны обрезаться при 320–390 px и увеличенном шрифте.
- Выделить общие компоненты: DataStatusBanner, EmptyState, ErrorState, EventListRow, EventStatusBadge, FilterBar, AppSheet.

На web ориентироваться на ширину доступной области: ориентир <600 — телефон, 600–1023 — промежуточная компоновка, от 1024 — sidebar/desktop. Точные точки проверить по контенту. Правило shortest-side для native-планшетов можно сохранить отдельно.

Для web-каталогов ограничить ширину примерно 960–1200 px, для длинного текста 60–75 символов в строке. Карту и сетку расписания разрешить расширять. Не растягивать каждую кнопку на всю ширину ноутбука.

## 8. Улучшения по экранам

### Главная

Существующие состояния до/во время/после фестиваля сохранить и уточнить. До фестиваля: дата и место, статус объявления программы, участники, подготовка поездки и сохранение offline. Во время: ближайшее личное событие, «Сейчас на сценах», быстрый переход в расписание/карту/помощь, важное изменение программы. После: явное завершение, архив, анонс следующего выпуска.

В фестивальном режиме уменьшить hero до компактного блока, чтобы полезная информация была на первом экране. Фоновое фото без старых дат либо явно архивное. Видео сохранять как необязательное украшение; текущую поддержку reduced motion и экономии трафика не потерять.

### Навигация

Предлагаемые пять постоянных вкладок: **Главная / Программа / Карта / Моё / Ещё**. Программа объединяет расписание, участников и автограф-сессии внутренними вкладками. Радио доступно через «Ещё» и компактный проигрыватель при воспроизведении. Помощь вынести на главную, карту и в начало «Ещё».

Стабилизировать порядок и наличие разделов между фазами фестиваля. Если программа не опубликована, показать соответствующий экран вместо исчезновения пункта. Для новых названий сохранить старые deeplink и корректную историю Back.

### Расписание

На телефоне по умолчанию список по времени: интервал, артист, сцена, статус, отдельная звезда. Сетка остаётся переключаемой; на большом экране может быть основной.

Добавить поиск артиста, фильтр сцены, «Сейчас», «Только моё». Сохранить выбранный день и позицию списка при просмотре деталей. Видно полное время; длинное имя переносится осмысленно. Одинаковая логика ночного дня и демовремени: автопрокрутка сетки сейчас использует `new Date()`, хотя подсветка получает `now`.

В модели выступления добавить status (`scheduled`, `delayed`, `cancelled`), revision/updatedAt и при необходимости прежнее время. Отмена должна оставаться видимой с объяснением, а не просто исчезать из избранного.

### Моё

Сделать персональный план: выступления и автографы в одной временной ленте с фильтром типа. Подсветить пересечения и недостаточное время перехода между сценами; не удалять выбор автоматически. Добавить кнопку в пустое состояние, отмену случайного удаления, экспорт/ссылку на план. Синхронизацию через аккаунт рассмотреть позже, только при подтверждённом спросе.

Уже есть food-favorites в контексте, но MySchedule показывает выступления и автографы. Перед расширением явно определить, где пользователь видит сохранённую еду и отдельно сохранённые треки.

### Карта

Сохранить уже реализованные маршруты, категории и «Машина и палатка». Добавить постоянный доступ к помощи и доступный текстовый список точек как альтернативу визуальной карте. Крупные подписи сцен/входов, краткая легенда, выделение выбранной точки.

Офлайн-режим должен показывать собственную схему территории, точки и путь по локальному графу, если данные скачаны. Не рассчитывать на доступность внешней подложки Яндекса. Состояния: GPS выключен, отказ в разрешении, низкая точность, пользователь вне территории, маршрут недоступен, проход закрыт, ошибка внешней карты. В UI не считать карту загруженной просто по истечении 8 секунд: сейчас такой timeout есть в FestivalMapScreen.

### Участники и карточка артиста

Архив уже реализован, но сделать его более явно отделённым от будущего состава. Предложить две области: «Этот фестиваль» и «Архив». Для актуального состава приоритет — выступление и сцена; Last.fm-счётчики убрать из основного ряда либо сократить и подписать источник.

В деталях артиста первым блоком сделать все его события текущего фестиваля с добавлением в план и переходом на карту; биография, похожие артисты и треки — ниже. Для неанонсированной программы не подставлять архивные события как текущие.

### Радио

Сохранить добровольный запуск воспроизведения. Добавить компактный плеер между экранами, восстановление после прерывания связи и понятное разделение: аудиопоток недоступен / только метаданные недоступны. В локальном просмотре ошибка метаданных уже показана и есть «Повторить»; это положительное состояние, а не доказательство поломки production-радио. Проверить экран блокировки, фоновое воспроизведение и аудиопрерывания на устройствах.

### Фудкорт

Сейчас есть категории, карточки и меню. Добавить поиск, фильтр по открытому времени и реальное «рядом со мной», только если точка связана с географией и получена позиция. Цена от, часы и расположение должны иметь структурированные данные вместо свободных строк. Опции питания/оплаты публиковать только из проверенного контента организаторов. Переход к точке карты сделать очевидным.

### Помощь, правила и настройки

Содержание помощи уже хорошо ориентировано на действия; основная проблема — обнаружимость. Надпись «Работает без интернета» уточнить: инструкции/сохранённая схема доступны offline, первый запуск и внешние карты имеют другие условия. Не обещать работоспособность непрогретого lazy-экрана без сети.

В правилах — поиск по темам и краткие ответы перед длинными текстами. В настройках — явный статус скачанных данных, последняя синхронизация с датой, объём кэша, уведомления. Демо перенести в группу «Демонстрация», сохраняя яркую маркировку и отдельные тестовые данные.

## 9. CMS: от форм редактирования к управлению публикациями

Сейчас есть полноценные редакторы, фильтры расписания, изображения, сортировки и сложный редактор карты с undo/redo. Следующий этап:

1. Черновик → предпросмотр → публикация; дата/автор публикации.
2. История изменений, восстановление предыдущей редакции и защита от конкурирующих записей.
3. Проверка перед публикацией: даты в пределах выпуска, существующие артисты/сцены, конфликт на сцене, битые ссылки, обязательные поля и ошибки геометрии.
4. Состояния «сохранение/сохранено/ошибка», предупреждение об уходе с несохранёнными изменениями.
5. Быстрое изменение времени/сцены, перенос с объяснением и показ затронутой аудитории. Изменение расписания и массовая рассылка — отдельные действия.
6. Импорт CSV со сверкой и предпросмотром разницы. Экспорт текущей версии программы.
7. Роли редактора, администратора и отправителя рассылок по мере появления команды.
8. Push: предпросмотр, тестовая аудитория, очередь, прогресс, результаты; сохранить существующее подтверждение.
9. Карта: отдельно конфигурация, геометрия, POI, эксплуатационные закрытия. Разделить большой MapDrawEditor на инструменты/слои/выделение/history, сохранив текущие функции.

Не требуется немедленно раскладывать весь JSON по десяткам таблиц. Первым шагом достаточно revision, валидации, снимков и атомарной записи. Нормализацию БД выбирать после понимания редакторской нагрузки.

## 10. Архитектура, производительность и эксплуатация

### Код

По мере изменений выделять модули festival, schedule, map, favorites, radio, notifications. UI, доменная логика, API и storage должны иметь понятные границы. Не устраивать общий перенос файлов без функциональной причины.

Оперативные изменения не должны зависеть от полного архива Last.fm. Для MVP достаточно компактного version endpoint/ETag и контролируемого polling; WebSocket нужен только при обоснованной необходимости. Обновление не должно менять выбранный день и прокрутку.

Снять baseline production-сборки: старт, готовность расписания, переход в карту, объём JavaScript, API transfer size и количество запросов. На native проверить JS/UI frame time, память и расход батареи. Не заменять измерения количеством useMemo.

Добавить сбор ошибок клиента и API с версией релиза, requestId и без токенов/точной геолокации в диагностике. Отдельно отслеживать загрузку данных, доступность маршрутов, время очереди push и ошибки медиа.

PR-check workflow: lint, typecheck обоих пакетов, все быстрые тесты, проверка версий, сборка. Сейчас основной workflow привязан к master/workflow_dispatch. Добавить staging с тестовой БД, запретом реальных массовых рассылок и отдельной конфигурацией.

План восстановления должен включать БД, uploads, конфигурацию и совместимость миграций. Создание копий недостаточно: требуется успешный тест восстановления в изолированное окружение.

## 13. Критерии приёмки

### Данные и сервер

- Некорректная дата/геометрия/ссылка на артиста отклоняется до записи.
- Два редактора одной версии не перезаписывают молча друг друга.
- Изменение времени не удаляет пользовательское избранное; отмена видна.
- Название выпуска и даты совпадают в приложении, API, CMS и SEO.
- Ошибка API не раскрывает внутренние детали; logs содержат requestId.

### Пользовательский интерфейс

- 320, 360, 390, 768, 1024, 1280 px: читаются полные подписи навигации и время.
- Длинное имя артиста, 200% увеличение текста и короткое выступление не ломают карточку.
- Главная, программа, карта, моё и помощь доступны понятными короткими путями.
- Фокус после перехода оказывается в новом контенте; модальное меню управляется клавиатурой и корректно возвращает фокус.
- Указание сцены/статуса не зависит только от цвета; проверить VoiceOver/TalkBack и desktop-screen reader.

### Офлайн и уведомления

- Первый запуск без сети сообщает, что данные ещё не скачаны, и не показывает выдуманную программу как актуальную.
- После явного скачивания перезапуск без сети открывает расписание, избранное, помощь и собственную схему.
- Включение Web Push не отключает offline; обновление worker сохраняет нужную функциональность и подписки.
- Сбой API 500, timeout, 429 и quota storage не уничтожает last-known-good.
- Проверить повторные события, перенос, отмену, смену года и ночное выступление после полуночи.
- Реальные доставки и deeplink проверяются отдельно на iOS/Android/PWA; успешный unit-тест не означает успешную доставку.

### Эксплуатация

- Новый релиз проходит health check, неуспешный возвращается на предыдущую версию.
- БД и uploads восстановлены из копии в изолированной среде.
- Критические тесты выполняются до merge, а не только после push в master.
- Согласованы реальные цели нагрузки; нет заявлений о готовности к количеству посетителей без испытаний.

## 14. Метрики результата

Зафиксировать baseline перед изменениями. Начальные продуктовые цели для проверки на 5–8 участниках: найти нужное выступление за 10 секунд; добавить в план одним действием из списка; найти помощь с главной/карты одним действием; отсутствие обрезанного времени на 390 px.

События аналитики: поиск и нулевой результат, добавление/удаление избранного, открытие маршрута, успешное скачивание offline, ошибка синхронизации, просмотр изменения программы. Сейчас просмотренный webAnalytics отслеживает page views; сценарные события дадут более полезную картину.

Технические метрики: доля успешных загрузок расписания, возраст сохранённой версии, время готовности критических экранов, ошибки JS/API, доля ошибок push и восстановления offline. Для каждого показателя нужны версия релиза и платформа, но не персональные данные посетителей.

## 15. Что оставить за пределами первого этапа

- Полное переписывание на другой frontend/router.
- Аккаунт и обязательная регистрация для просмотра программы.
- Микросервисы и сложная инфраструктура без измеренной нагрузки.
- Массовый рефакторинг всех файлов одновременно с редизайном.
- Дополнительные анимации до исправления читаемости и надёжности.
- Новые коммерческие функции до проверки основных фестивальных сценариев.

Главный ориентир следующей версии: посетитель быстро понимает, что происходит, успевает на выбранное событие и получает нужную информацию даже при плохой связи.
